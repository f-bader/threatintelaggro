# Repository guidance

## UI changes

- Apply the repository's [Threat Intel Aggro UI skill](.agents/skills/threat-intel-aggro-ui/SKILL.md) when changing the web UI. Preserve its existing visual language and review workflow.
- Review the actual rendered page, not just the markup or a passing build. Use an isolated local database populated with representative fixtures; do not change the live database, approvals, or feed settings during visual checks. Use mock provider responses and avoid spending AI credits during ordinary tests.
- Include realistic long IOC values, source titles, descriptions, and original roles in the fixtures. For IOC changes, inspect context-only, approved, unapproved, suspicious, malicious, and analyst-classified indicators, including their action controls and status messages. Check empty and populated filter results.
- Verify desktop, tablet, and narrow mobile layouts (for example, 1280, 768, and 390 CSS pixels wide). Inspect the relevant expanded and collapsed states and confirm that text, status badges, dropdowns, links, and buttons do not overlap or clip. Inputs and buttons in an action row should have consistent heights and aligned baselines; controls must remain usable when they wrap.
- Use the built-in browser's viewport override to check responsive UI at 1280, 768, and 390 CSS pixels wide; do not approximate these sizes with browser zoom or screenshot scaling. At desktop and tablet widths, compare relevant control top edges and baselines with `getBoundingClientRect()`; at mobile width, verify that wrapped controls remain visible and usable. Reset the viewport override after review.
- For forms built from CSS grid labels, helper text must not shift adjacent controls vertically. Set the outer form grid to `align-items: start` and label grids to `align-content: start`; then compare the rendered control top edges and baselines within each row using `getBoundingClientRect()` at desktop and tablet widths. A no-overflow check alone does not establish alignment.
- Check both appearance and geometry: confirm that the page does not scroll horizontally, except for an intentionally scrollable wide table or code block. Inspect long labels, selected dropdown text, and action buttons at each viewport. Use text labels as well as color to communicate classification; make suspicious and malicious states visually distinct.
- Exercise the changed interactions in the browser with disposable fixtures. For filters, verify the displayed records, available facet options, filter persistence after actions, and matching CSV/API results where applicable. Context-only indicators must not enter actionable API or CSV output merely because the UI displays them. Preserve original roles and approval state when testing classification and reset.
- Add focused regression tests for meaningful behavior changes, including classification, filtering, persisted review state, and export/API behavior when affected. Run the relevant tests; for the current .NET suite, use `dotnet test tests/ThreatIntelAggro.Tests/ThreatIntelAggro.Tests.csproj --configuration Release`. A successful test run does not replace visual inspection.
- Report the checks performed and any untested browser, viewport, provider, or deployment behavior. If browser validation is unavailable, say so rather than claiming the layout was verified.
